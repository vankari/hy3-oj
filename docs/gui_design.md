# 图形界面设计方案（Streamlit）

## 当前实现（2026-09-09）

界面已改为单一对话工作区，以下早期多页设计仅作历史参考。

- 暖白背景、深绿强调色、适合阅读题解的对话栏；首页只提供通用输入，不展示具体题目入口。整数分解题留作视频录制时手动提交的样例。
- 侧边栏按“今天 / 昨天 / 近 7 天 / 更早”列出题目标题，支持搜索。点击直接恢复完整对话，URL 中的 chat 标识支持刷新后恢复。
- 新对话使用独立 ID，消息、题面、代码、审查与题解持久化到 runs/ui/conversations/；运行轨迹使用独立目录，避免同名题面覆盖。
- 后台线程在任务完成或失败时保存，刷新后可连接同进程中的任务；服务重启后的未完成任务明确提示重新提交，不假装续跑成功。
- 兼容旧单题 JSON；旧记录没有原始题面时如实说明。批量 JSONL 置于折叠区，不完整行不会阻止其他记录打开。
- 结果保留“题解 / 代码 / 过程评估”三个页签，人工反馈折叠。判题状态和过程审查状态独立展示，并提供组合状态。
- 判题器唯一决定 AC 与否；Reviewer 主要审查最终题解、计划与可见解题轨迹，代码只用于核对实现一致性，不执行判题或修改结果。
- 顺序为“解题与判题 → 生成最终题解 → 过程审查 → 组合状态”。题解哈希绑定审查版本，题解被修改或旧审查未覆盖正文时显示待审查。
- 组合状态为“结果通过·过程通过 / 结果通过·过程有误 / 结果未通过·过程通过 / 结果未通过·过程有误”；缺少判题或有效审查时等待完整评估。
- 题面、题解和审查证据统一使用数学 Markdown；兼容历史裸 LaTeX、常见复杂度写法及括号定界符，保护代码和链接。新题解直接输出标准美元符号公式。
- 不提供通用追问能力：输入框提交新的题目，历史对话保存已有解题记录。

验证：HistoryStore 单测、Streamlit AppTest 覆盖历史点击、刷新恢复、新建对话、后台成功/失败落盘和多条批量详情展开。

## 一、定位

任务书 R9 要求"时长 2 分钟以内的 demo 视频或 GIF，展示一次完整的解题与过程评估流程"。
GUI 是**该 demo 的载体**，同时整合项目全部核心能力，供评审直接体验。

## 二、页面结构（左侧导航多页）

```
Hy3-OJ 控制台
├── 1. 解题工作台（主页面，demo 主场景）
│   ├── 题目输入：① 外部文件(md/txt) ② 粘贴文本 ③ 数据集选题
│   └── 一键运行 → 实时展示：解析 → 规划 → 生成 → 判题 ⇄ 修复 → 审查 → 题解
├── 2. 过程评估详情（五段式审查 + 蒙对检测的可视化）
├── 3. 评测看板（LCB/CodeContests 分层结果、pass@k、能力临界点）
├── 4. 人类反馈（对评估结论判定 real/false_positive，驱动迭代）
└── 5. 设置（模型/端点/并发/沙箱参数）
```

## 四、关键技术决策

| 问题 | 决策 | 理由 |
|---|---|---|
| 长时间运行的进度反馈 | 同步执行 + `st.status` 分步展开 | Streamlit 每次交互重跑脚本，async 在后台线程需额外管理；同步+状态容器最简单可靠 |
| 中断支持 | 复用 `GracefulInterrupt` + 「停止」按钮 | 已实现的协作式中断，按钮置位即可 |
| 结果持久化 | 每次运行落 `runs/ui/<id>.json`，页面可从历史恢复 | 避免刷新丢结果 |
| 密钥 | 仅从 `.env`/环境变量读，界面**不提供**输入框 | 任务书硬性要求：密钥不得入库、不落界面 |
| 图片题面 | 实验性：显示「含 N 张图片未解析」告警 | 视觉模型未开通，如实标注而非静默忽略 |

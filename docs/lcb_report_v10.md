## 关键工程发现

### 1. call-based 判题协议四层根因（LeetCode 风格题 23 道）

| # | 根因 | 修复 | 症状 |
|---|---|---|---|
| 1 | Coder 提示词固定"stdin 读入"与 call-based 冲突 | 协议自适应提示词 | 模型写 `input()` 解析遇 JSON 崩溃 |
| 2 | 模型漏写驱动入口 | `ensure_driver` 自动补挂 | 全部测试点 RE |
| 3 | 驱动整体 `json.loads` 后展开 | 逐行解析 | `takes 2 but 4`（3677） |
| 4 | 模型复制旧整体解析驱动绕过修复 | **强制剥离 `__main__` 后注入** | `takes 2 but 3`（3532/3552） |

前 3 条未根治（存量轨迹仍用旧驱动），第 4 条才彻底闭环——这解释了 v7(+8.7pt on call-based)
与 v8(+11.7pt 总体) 的差异。**call-based 题通过率：56.5% → 65.2%。**

### 2. C++17 兜底与一个隐蔽的循环 bug

v9 引入 C++ 兜底（Python 轮数耗尽后 hard 档切 C++17），但**触发 7 题、救回 0 题**。
轨迹实证（`atcoder:arc181_c`）：`CPP_FALLBACK` 事件后**无任何 `JUDGED`**——代码生成了却从未判题。

根因：`for round_idx in range(max_rounds + 1)` 中赋值 `round_idx = -1`，
会被 `continue` 后的迭代器覆盖，range 耗尽即结束循环。

修复：改 `while` 手动管理轮数；同时修 reflector 语言透传（C++ 路径下按 Python
提取代码块会把 C++ 悄悄换回 Python）。**v10：触发 7 题、救回 2 题**（abc306_e、arc183_c）。

### 3. 采样预算分配：多样性不能牺牲深度

v5 把 k 均分给 3 个 plan，导致每 plan 仅 2~4 样本、单思路深度不足反而掉分（−10pt）。
修正为主 plan 占 60%，兼顾深度与多样性。

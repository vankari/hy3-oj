> 来源：`犀牛鸟开源-实战任务-混元大语言模型项目.pdf`（4 页，pypdf 提取）。

## 一、任务书要点（原文摘录）

### 通用要求（两个任务共用）

- 自行创建并维护开源项目仓库（GitHub 公开仓库），**无需向 Hy3 官方仓库提 PR**；完成后提交仓库链接
- README 需写明项目介绍、运行方式与环境要求
- **不得将 API Key 等密钥硬编码或提交进仓库**，需通过环境变量或配置文件传入
- 项目命名与 README 中需标注为**个人/活动作品**，避免被误认为腾讯官方发布
- 模型能力调用通过 Hy3 完成，**不需要训练或微调模型**

### 场景二任务描述（算法竞赛方向）

> 基于 Hy3 构建一个面向可验证场景的 AI 应用，场景领域需存在标准答案，如科学学科、算法竞赛、代码功能等。在此基础上设计一套面向可验证场景的**过程评估方法**：除判断最终答案的正确性外，还需**评估推理过程是否成立、定位错误发生的步骤、归纳错误类型**，并识别**最终答案正确但推理过程无法支撑该结论**的样本。

方向选择（原文）：「算法竞赛：给定题目与测试数据，评估解法思路、复杂度分析与边界处理」。

### 场景二硬性要求清单

| # | 要求 | 原文依据 |
|---|---|---|
| R1 | 可运行应用：针对题目产出**完整解答过程**，而非仅输出最终答案 | 「应用侧」 |
| R2 | 评测题集：每题有标准答案 + 可自动校验判定；**按难度分层**（基础→高难度）；说明来源、构造方式、分层依据 | 「评测题集」 |
| R3 | 过程正确性判定：推理链是否成立，有无跳步、循环论证、误用定理、条件遗漏、幻觉 | 「过程评估设计」 |
| R4 | 错误步骤定位：解答错误时定位错误**开始出现**的步骤 | 同上 |
| R5 | 错误类型归类：建立错误分类体系（题意误读、概念理解错误、计算错误、条件遗漏、跳步推导、格式不符等） | 同上 |
| R6 | **结果正确但过程不成立**的样本识别：猜中选项、数值巧合、误用定理却得出正确结果、恰好通过测试但实现逻辑有缺陷 | 同上 |
| R7 | 过程评估器有效性验证：**定位准确率**（错误样本上能否定位到实际出错步骤）+ **误报率**（正确样本被判过程有问题，人工抽检真实问题/误报比例） | 「过程评估器的有效性验证」 |
| R8 | 结果分析：最终答案准确率、过程正确率、错误类型分布；**按难度分层分析**，指出模型表现开始明显下降的难度区间 | 「结果分析」 |
| R9 | 产出：开源仓库（应用源码 + **过程评估模块**）、评测材料（分层题集+标准答案+校验脚本+过程评估脚本）、完整结果、有效性验证数据及**人工抽检记录**、分析报告（过程评估方法设计依据、错误分类体系说明、典型案例、能力边界与临界点）、**≤2 分钟 demo 视频/GIF** 展示完整解题与过程评估流程 | 「产出」 |

## 三、对齐结论

1. **主闭环设计（解题）依然成立**——任务书把解题应用当作载体，现有 Parser/Planner/Coder/Reflector 闭环与 Generate-and-Test 思路完全兼容。
2. **最大缺口是"过程评估"维度**（R3–R7）：需要新增一个与 Reflector 平行的 **Reviewer Agent（过程评估器）**，以及配套的**双层错误分类体系**、**蒙对检测规则**、**定位准确率/误报率验证方法**。这也恰好是本项目区别于"又一个刷题 Agent"的差异化亮点。
3. **已有资产的复用**：闭环轨迹（Plan/代码/判题/反思 jsonl）正是过程评估的天然输入；Reflector 的四类归因可升级为双层错误分类的结果层。
4. **时间影响**：16 天窗口内需挤出 Reviewer + 有效性验证的工作量。缓解措施：Reviewer 复用 llm 层与 prompts 体系；有效性验证的"定位准确率"用**自动注入 bug**构造 ground truth（无需人工），仅误报率需小规模人工抽检（~50 题量级，可接受）；Demo 与评测报告优先级高于 C++17 扩展（C++17 明确降为 stretch goal）。
